 ● Suppose the original invertible transform is:

   F(x, y) = (x + y, x - y)

   Fixing  y = 2  produces:

   H(x) = F(x, 2) = (x + 2, x - 2)

   To invert a valid output  (u, v) , evaluate the original inverse:

   F⁻¹(u, v) = ((u + v) / 2, (u - v) / 2)

   Then discard the recovered  y . This works when  (u, v)  lies on the fixed slice, meaning  (u - v) / 2 == 2 .

   The risk arises for an arbitrary output such as  (10, 10) :

   F⁻¹(10, 10) = (10, 0)

   Dropping the recovered fixed coordinate returns  x = 10 , but:

   H(10) == (12, 8) != (10, 10)

   Thus the projected operation is a left inverse:

   H⁻¹(H(x)) == x

   but not a full inverse over the output space:

   H(H⁻¹(output)) == output

   You cannot pass  y = 2  into  F⁻¹ , because  F⁻¹  accepts only  F ’s output coordinates. Instead, we can apply  F⁻¹ , verify that
   its recovered fixed coordinates equal the required values, then return the free coordinates. This gives a useful analytical
   inverse on the fixed transform’s image and explicitly rejects off-slice world coordinates.

   The simplest example is fixing  y = 0  in the identity:

   H(x) = (x, 0)

   Its projected inverse can map  (x, 0)  back to  x , but  (x, 5)  has no inverse under  H . Silently returning  x  would make
    world_to_pixel  claim success for an unreachable world coordinate.

 ● Python takes the most conservative option:

   • Astropy’s  fix_inputs(model, ...)  creates a lower-input  CompoundModel , but  CompoundModel.inverse  returns  NotImplemented 
     for the  fix_inputs  operator. Even an identity transform fixed from  2 → 2  to  1 → 2  reports no analytical inverse.
   • Python GWCS consequently has no  backward_transform . It attempts numerical inversion, but its numerical solver explicitly
     rejects unequal pixel/world dimensions. Therefore a fixed-input WCS is effectively forward-only for this case. The reference
     implementation does not accept or reject off-slice outputs because it cannot invert either valid or invalid outputs.
   • The Python WCS wrapper also retains the original input frame after reducing the transform’s input count, creating inconsistent
     dimensional metadata in the versions examined. GWCS.jl should not copy that behavior.

   The implementation options are:

   1. Python parity: return  NoInverse() . This is safest and simplest, but  world_to_pixel  cannot work because GWCS.jl’s numerical
      inverse likewise requires equal dimensions.
   2. Unchecked projected inverse: evaluate the original inverse and discard recovered fixed coordinates. This is fast and correctly
      inverts outputs on the slice, but silently maps unreachable off-slice outputs to misleading pixels.
   3. Checked projected inverse: evaluate the original inverse, verify its recovered fixed coordinates match the configured constants
      within a documented tolerance, then return the free coordinates. Valid points get a fast analytical inverse; unreachable
      points raise a domain error instead of producing false results.
   4. Rectangular numerical inversion: solve the reduced, generally overdetermined system using least squares and require a small
      forward residual. This handles transforms without analytical inverses too, but substantially expands the numerical-inversion
      scope and is unnecessary when the original inverse exists.

   I recommend option 3 for this feature, while leaving general rectangular numerical inversion as a separate checklist item.

 ● Generic annotation wrapper

   Example shape:

   NamedTransform(transform; name, inputs, outputs)

   with public  transform_name ,  input_names , and  output_names  accessors.

   Pros

   • Keeps numerical transform types focused on evaluation parameters.  Shift  stores only its offset;  AffineTransform  stores only
     its matrix and offset.
   • Applies uniformly to built-in and external  AbstractTransform  subtypes. External packages do not need to redesign their structs
     merely to participate in naming.
   • Separates semantic annotations from mathematical identity. The same transform instance can be reused under different axis names.
   • Centralizes validation of name counts, uniqueness, and composition compatibility.
   • Avoids repeating three metadata fields and constructor plumbing across every transform type.
   • The wrapper call can inline to the wrapped transform, so scalar evaluation should remain allocation-free.
   • Compilation can preserve the outer annotation while optimizing or replacing the wrapped numerical implementation.

   Cons

   • Adds another node and type layer to transform trees.
   • Requires forwarding methods for evaluation, inverse, Jacobian, and compilation.
   • Repeated annotation can create nested wrappers unless constructors normalize them.
   • Code inspecting concrete transforms may need  parent_transform  or  unwrap_transform .
   • Naming behavior during composition still needs explicit rules; the wrapper alone does not solve those semantics.

   Fields directly in every transform

   Example shape:

   struct Shift{T} <: AbstractTransform{1,1}
       offset::T
       name::Union{Nothing,String}
       inputs::NTuple{1,String}
       outputs::NTuple{1,String}
   end

   Pros

   • Names are visibly part of every built-in transform object.
   • No extra wrapper node when displaying or serializing a transform.
   • Direct field access is straightforward for built-in types.
   • Each transform constructor can expose naming keywords naturally.
   • A transform’s numerical parameters and annotations travel together automatically.

   Cons

   • Julia abstract types cannot require fields. External  AbstractTransform  subtypes would still need an accessor protocol, so
     direct fields do not eliminate that abstraction.
   • Repeats metadata storage and constructor logic across every transform type.
   • Increases the size of every transform, including anonymous internal transforms in performance-oriented pipelines.
   • Every new transform implementation must remember identical validation and metadata behavior.
   • Fusion and compilation become awkward: combining two named  Shift s into an  AffineTransform  must reconstruct or discard fields
     whose meaning may no longer be valid.
   • Reusing one numerical transform under different axis names requires copying/reconstructing it.
   • Composite transforms need different naming semantics from leaf transforms, so uniform fields are less uniform than they
     initially appear.

   Best design: use a hybrid protocol centered on accessors, with a generic annotation wrapper as the standard storage mechanism. A
   specialized external subtype may store names itself and override the accessors, but built-in mathematical types remain lean. This
   provides first-class names for all transforms without forcing metadata fields into every numerical representation.

   └ They are not mathematically equivalent, even for scalars.

     Julia uses:

      abs(value - key) <= max(atol, rtol * max(abs(value), abs(key)))

     Python GWCS uses NumPy  isclose(key, value) , whose rule is:

      abs(value - key) <= atol + rtol * abs(value)

     For  value=1000.109 ,  key=1000 ,  atol=0.1 ,  rtol=1e-5 , the difference is  0.109 :

      - Julia threshold:  max(0.1, 0.01000109) = 0.1 , so  isapprox  is false.
      - NumPy threshold:  0.1 + 0.01000109 = 0.11000109 , so it is true.

     The explicit expression preserves Python GWCS metadata behavior. If Julia-native approximate equality were intended,  isapprox 
     would indeed be preferable.
